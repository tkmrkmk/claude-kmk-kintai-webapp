# アーキテクチャ

## 要件

- フロントエンドのみ（バックエンド通信を行わない）
- 軽量 (スマホのみで動作する)

## 構成

- 静的ファイルのみで構成し、静的ホスティング（GitHub Pages 等）で配信する。
- 永続化は LocalStorage のみ。DB・APIサーバを持たない。
- Service Worker でアセットをキャッシュし、オフライン起動を可能にする。

## 技術選定

### 採用: Svelte 5 + Vite（SPA構成）

| 項目 | 選定 |
|---|---|
| UIフレームワーク | Svelte 5（runes） |
| ビルドツール | Vite |
| 言語 | TypeScript |
| ルーティング | なし（単一ページ + 画面切替） |
| 日付処理 | 標準の `Date` / `Intl` のみ（日付ライブラリを入れない） |
| 永続化 | LocalStorage |
| オフライン | Service Worker（アセットのプリキャッシュ） |

### 選定理由

- **コンパイラ方式のためランタイムが最小**（gzip 5KB前後）。フォームやカレンダーのように状態の多いUIを書いてもランタイムがほとんど増えない。
- runes（`$state` / `$derived`）により、LocalStorageへの同期・実働時間の自動計算・未入力日のマーク表示といった「状態に応じた再描画」をフレームワークに任せられる。本アプリのUIはこの性質が支配的であり、選定の決め手とした。
- SvelteKit は採用せず **Vite + Svelte の SPA** とする。出力が静的ファイルのみで完結し、GitHub Pages にそのまま配置できるため。

### 他案の比較（不採用）

| 案 | ランタイム(gzip概算) | 不採用の理由 |
|---|---|---|
| Preact + Signals | 〜6KB | Svelteとほぼ同等。React経験を流用する必要がないため見送り |
| Vanilla TS | 0KB | カレンダー再描画とフォーム状態同期の自前実装が保守負債になる |
| Alpine.js | 〜15KB | TypeScriptが使えず、TSVパース・バリデーション・振休残計算を型なしで書くことになる |

### サイズに関する前提

成果物サイズを支配するのはフレームワークではなくアプリ本体のコード（カレンダーUI、TSV生成/パース、バリデーション、設定画面）で、gzip後 20〜50KB 程度を見込む。総量は 30〜70KB gzip に収まり、Service Worker のキャッシュにより2回目以降の転送は発生しない。

このため、サイズ最適化として優先度が高いのは**依存ライブラリを増やさないこと**であり、特に日付ライブラリ（dayjs / date-fns 等）は導入しない。年度日付の計算は加減算と曜日判定が中心であり、標準APIで十分に賄える。

## データモデル（案）

```jsonc
{
  "fiscalYear": 2026,
  "settings": {
    "defaultPattern": { "start": "09:30", "end": "18:30", "break": "1:00" },
    "presets": { "work": ["AIプロダクト（自宅）"], "note": ["★草加↔築地"] }
  },
  "days": {
    "2026-04-01": {
      "type": "通常勤務",      // 勤怠区分
      "start": "09:30",        // 開始
      "end": "18:30",          // 終了
      "break": "1:00",         // 休憩
      "work": "井口さん面談、AIプロダクト（本社）", // 作業内容(作業場所)
      "note": "★草加↔築地"    // 備考
    }
  }
}
```

- LocalStorage のキーは年度単位で分離する（例: `kintai:2026`）。
- 日付キーは `YYYY-MM-DD`。未入力日はキーを持たない。
- 時刻は `H:mm` の文字列で保持し、計算時のみ分に変換する。
- 各フィールドは Excel の `年間入力シート` の列に1対1で対応する（対応表は `doc/excel-format.md` を参照）。
